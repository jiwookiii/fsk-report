# 보안 보고서 게시 사이트 (GitHub Pages · Git 배포 · v4)

경영실적 보고서를 암호화해 GitHub Pages에 올리고, 계정이 있는 사람만 열게 하는 저장소.
**이 폴더 전체가 공개 저장소**. 원본 보고서·엑셀·관리자 키·계정 정보는 `../build/`(비공개)에만 둠.

## 사용자 화면 (`index.html`)

- 로그인하면 열 수 있는 모든 판(월·결산 버전)이 최신순으로 보이고 최신판이 열림. 오른쪽 아래 막대에서 이전 판·지난달 보고서 선택, 인쇄, 비밀번호 변경, 로그아웃.
- 화면 전체에 계정별 워터마크(회사 / 부서 / 사번 / 성명).
- **비밀번호 변경**: 현재·새 비밀번호를 넣으면 "변경 코드"가 나옴 → 관리자에게 메신저로 전달 → 관리자가 반영·게시한 뒤부터 새 비밀번호로만 열림. 코드에는 비밀번호가 없고, 사용자의 현재 키로 서명돼 있어 남이 대신 만들 수 없음.

## 파일

| 파일 | 내용 |
|---|---|
| `index.html` | 로그인·판 선택·비밀번호 변경 화면 |
| `data/keys.json` | 계정 목록: 아이디 해시, 비밀번호로 잠근 개인키, 공개키, 관리자 공개키 |
| `data/catalog.json` | 판 목록: 판마다 계정별로 잠근 판 열쇠·워터마크, 판 열쇠로 잠근 설명(월·버전·게시일·변경 요약) |
| `data/r/<판>.enc.json` | 판 본문(판 열쇠로 암호화) |
| `deploy.ps1` / `deploy.cmd` | Git 게시: 원격 최신화 → 점검 → 커밋·푸시 → 사이트 반영 확인 |
| `tools/check-site.mjs`, `.githooks/pre-commit`, `.githooks/pre-push` | 공개 전 점검(허용 목록 밖 파일·평문·개인키·형식 오류 차단). 커밋마다, 푸시되는 커밋마다 실행 |

## 관리 작업 (build 폴더에서, Node.js 필요)

| 하려는 일 | 명령 |
|---|---|
| 새 판 게시 | `node tools/site.mjs add --html 10월_영업이익_추정비_분석.html --month 2026-11 --label "결산 v0.5" --date 2026-12-10 --summary "변경 요약"` |
| 계정 추가·정보 수정 | `node tools/site.mjs users --csv 계정목록.csv` (기존 계정 비밀번호는 건드리지 않음. 비밀번호 칸이 빈 신규 계정은 임시 비밀번호 자동 생성 → `secrets/임시비밀번호_*.csv`) |
| 계정 삭제 | `node tools/site.mjs remove <아이디>` 또는 `users --csv … --prune` |
| 비밀번호 변경 코드 반영 | `node tools/site.mjs apply <코드>` (코드가 길면 파일로 저장 후 `apply @파일`) |
| 비밀번호 분실 | `node tools/site.mjs reset <아이디>` → 임시 비밀번호 전달, 사용자가 로그인 후 직접 변경 |
| 현황 / 점검 | `node tools/site.mjs list`, `node tools/site.mjs verify [--csv 계정목록.csv]` |

그다음 이 폴더에서 `.\deploy.ps1 -Message "…"` (또는 `deploy.cmd` 더블클릭).

- 계정 추가: 모든 판을 새 계정에도 열리게 다시 잠금.
- 비밀번호 변경 반영·재발급·계정 삭제: **모든 판의 판 열쇠를 새로 만들어 본문까지 다시 암호화**. 그래서 이전 비밀번호나 저장소 이력 속 예전 열쇠로는 그 뒤 게시된 파일을 열 수 없음. 판마다 약 2MB가 새로 커밋되므로 저장소가 조금씩 커짐.
- 관리 도구는 변경 직전 상태를 `build/secrets/backup/`(최근 5개)에 저장하고, 도중에 오류가 나면 자동 복원. 동시에 두 개를 실행하면 잠금으로 막힘.

**관리자 키 `build/secrets/admin.json`은 반드시 별도 백업**(사내 보안 저장소 등). 잃으면 기존 판을 새 계정에 열어 줄 수 없고 비밀번호 변경 코드도 반영할 수 없음. 이 파일은 저장소에 올리면 안 됨(점검 스크립트가 차단).

## 최초 설정 (다른 PC)

1. `git clone https://github.com/<소유자>/<저장소>.git` 후 `git config core.hooksPath .githooks`.
2. 저장소 Settings → Pages → "Deploy from a branch", `main` / `(root)`.
   (완전히 새 저장소에 처음 올릴 때는 예전 형식 커밋이 점검에 걸리므로, 현재 파일만 담은 새 이력으로 올릴 것)
3. 관리 작업을 하려면 `build` 폴더와 `build/secrets/`(관리자 키·계정 정보)를 비공개 경로로 옮겨 둠.

## 보안상 한계

- 암호문은 누구나 내려받을 수 있으므로 보호 수준은 비밀번호 강도에 달림(12자 이상 강제, PBKDF2-SHA256 60만 회).
- 저장소 이력에 과거 파일이 남음: 비밀번호를 바꾸거나 계정을 지워도, **그 전에 게시돼 있던 파일**은 이전 비밀번호로 이력에서 내려받아 열 수 있음(같은 내용). 변경 반영 후 게시된 파일은 열 수 없음.
- 보고서는 별도 출처로 격리된 화면(sandbox)에서 실행돼 로그인 화면·키에 접근할 수 없음.
- 직접 `git push`해도 `.githooks/pre-push`가 같은 점검을 함(`git config core.hooksPath .githooks` 필요). 공개 파일에 개인키 모양의 값이나 이 PC의 관리자 키 값이 있으면 거부.
- 접속 기록·로그인 시도 제한·즉시 차단 없음(서버가 없는 구조). 화면 캡처는 막을 수 없음(워터마크로 추적만).
- 로그인 화면 제목("보안 문서"), 계정 수, 판 수, 판 파일 크기는 공개됨. 판 파일 이름은 무작위라 월·버전이 드러나지 않고, 판의 월·버전·게시일·요약은 암호화됨.
- 고객사·손익 자료를 외부 서버에 두는 것이므로 회사 보안 승인 필요.

## 암호화 방식

- 판마다 무작위 256비트 판 열쇠로 본문을 AES-256-GCM 암호화.
- 계정마다 P-256 키 쌍. 개인키는 비밀번호(PBKDF2)로 잠가 `keys.json`에 둠. 판 열쇠는 판마다 새 일회용 키와 각 계정 공개키의 ECDH로 만든 키로 잠금. 관리자 키 쌍에도 같은 방식으로 잠가 두어 관리자가 판 열쇠를 다시 나눠 줄 수 있음.
- 비밀번호 변경 시 새 키 쌍을 만들고, 반영할 때 모든 판의 판 열쇠를 교체 → 새 공개키에만 열림.
- 모든 처리는 브라우저(Web Crypto)와 관리 도구(Node.js Web Crypto) 안에서만 이뤄짐.
